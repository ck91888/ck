# 本批资料关联查询读行优化

基线为已发布测试 `d0fbeb42bed9a6d6870cbce548f6593cf645f843`，功能分支 `feature/perf-batch-material-lookup-20261103`。仅本地合成数据和本地 workerd D1，未查询或修改线上业务数据，本批不发布。

## 原因与范围

原有关联作业查询只利用 `sop_records_kind(kind,department,updated_at)`。d0fbeb42 增加的同事务集合校验又执行 COUNT 和反向成员检查，因此一个入库计划的资料移除/恢复要三次扫描全部 need 历史。QA 夹具的 10423→30430 读行在独立夹具中复现为 10036→30061；数据组成不同，不能把两者当作同一次测量。

新增非唯一部分表达式索引 `ck_batch_material_inbound_needs_v1`：入库 need 按 source_id、department、updated_at 索引。后两个键及隐式 rowid 保持同计划作业在旧 kind 索引中的遍历顺序，包括时间相同和 ID 顺序不同的记录。原查询、事务内集合校验 SQL、逐单 revision CAS、权限、冻结引用检查、软移除、通知和历史事件均保留。

索引只在有权执行的资料移除/恢复通过参数、回执及文件版本检查后初始化。普通资料读取、非法请求、开关关闭和已提交回执重放不触发该建索引过程。`IF NOT EXISTS` 和成功初始化缓存支持已有库及两个冷绑定并发；失败不缓存，可重试。不删除旧索引，不增加唯一约束，不改写历史业务行。历史 need 的损坏 JSON 仍拒绝修改并保留原始数据；读取资料列表不会因新索引构建而新增失败。

## 合成性能证据

`tests/batch-material-lookup-performance.mjs` 使用真实登录 Worker API。每个规模先创建一份合成数据库，再分别复制到本地 workerd D1，运行前集合保护版77c5、当前d0fb、索引版。六张同计划作业含跨部门、同时间、关闭和取消状态；其它100/1000/10000张历史作业不属于本计划。四次操作为移除、恢复、移除、恢复，首请求与后三次分开计量。

每次比较响应 SHA256 和完整业务快照 SHA256（包括原始状态、事件 rowid 顺序、资料、下游、工时和成果），三个版本一致。不是只比较数量。两引擎的独立查询计划/行顺序断言另直接比较完整结果。

基本业务开关配置、本地无并行测试时的日常请求数据如下；API 耗时为后三次请求中位数：

| 无关历史 need | d0fb 总读行 | 索引版总读行 | 关联查询及集合校验读行（旧→新） | d0fb API ms | 索引版 API ms |
|---:|---:|---:|---:|---:|---:|
| 100 | 361 | 64 | 330→33 | 43.570 | 42.309 |
| 1000 | 3061 | 64 | 3030→33 | 37.013 | 36.688 |
| 10000 | 30061 | 64 | 30030→33 | 66.890 | 56.211 |

万条历史的日常请求总读行减少约99.8%，本机 API 中位耗时减少约16.0%。计量包含实际 API 的其它查询，收益不是网络或实体手机速度保证。复杂度仍与本计划关联作业数量有关，没有提前分页、漏掉关闭作业或以缓存跳过集合检查。

另在万条历史、返岗/自动派审/切日/共享等测试站业务开关全部启用时独立串行对比d0fb和索引版，日常总读行 **30076→79**，API中位数 **96.772→47.070ms**，约减少51.4%。额外验证已有索引之后的正常批资料上传，完整回执和快照仍一致，总读行10047→48、API76.663→59.133ms；该路径的代码和SQL没有修改。原集合检查仍为33读行，差额属于其它业务检查。本次全开关首次API为86256→74488读行、436.825→352.249ms，单独CREATE INDEX为18227读行/8007写行/12ms。日常写行40→44，均为本地D1元数据。

冷启动建索引有成本，不能隐藏：万条历史首次 CREATE INDEX 的 D1 元数据为18227读行、8007写行、11ms数据库时长（夹具中8006张为入库need）。完整首次API还包含其它初始化，当前d0fb为50810读行/185.011ms，索引版39041读行/160.662ms。日常资料操作写行36→40来自四张活动子单的索引维护，不是新增劳动或审计事件。没有远端大库容量/锁等待测量。

- 覆盖旧库双冷初始化、DDL故障重试、非唯一键、查询计划、原遍历顺序、JSON标量与损坏历史、回执只读、版本冲突、公共/归档/冻结引用、计划隔离、通知、取消与关闭开关。既有权限专项仍按原规则验证。

- 真实构建页面串行回归三个原脚本全部exit 0：`batch-material-reference-browser.mjs` 在1440/390验证冲突拒绝、原按钮同key重试、新单通知、恢复重开和冻结引用拒绝，返岗/派审等开关启用、页面错误0；`bulk-output-draft-browser.mjs` 验证普通/外部/分组/多单及跨设备草稿、版本冲突和最终修正，覆盖1440/390/320；`photo-compression-browser.mjs` 验证原压缩、重试、取消及布局矩阵，照片仍3462248→403880字节、2048×1536，条码和QR可识别，页面错误0。没有修改这三个既有脚本的断言或等待。

复现性能：设置 `CODEX_PRIMARY_RUNTIME_NODE_MODULES` 为包含 miniflare 的目录，`CK_MATERIAL_LOOKUP_MODULES` 为标签到各版本 `worker-v2/index.js` 绝对路径的 JSON，再运行 `node tests/batch-material-lookup-performance.mjs`。`CK_MATERIAL_LOOKUP_SIZES` 可选100/1000/10000，`CK_MATERIAL_LOOKUP_METRICS` 可写测量结果；`CK_MATERIAL_LOOKUP_STAGING_FLAGS=true` 可额外启用返岗、派审、切日等测试站开关。

回归入口：`node --test tests/batch-material-lookup.test.mjs tests/batch-material-reference-races.test.mjs tests/batch-material-state.test.mjs`；原生D1另设置 `CK_P1_NATIVE_D1=true`。日志及页面截图保存在工作区测试运行目录，不提交个人、业务或凭据数据。
