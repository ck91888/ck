## 双向竞争与第一阶段修复

1. 移除请求已读完同批作业列表，在提交事务前挂起；随后创建新作业并成功选择该资料，再放行旧移除。旧版仍返回removed=true。
2. 移除请求读完旧列表后创建新作业，新作业读到可用资料并在分组保存事务前挂起；旧移除先提交，再放行旧保存。旧版仍成功写入已移除资料的冻结引用。

两引擎均使用真实登录Worker API、本地合成SQLite或workerd D1：修复前 **0通过/2失败/0跳过**，失败即两项非法成功，日志保留在本地。并非只对原有作业做版本CAS就足够：初次列表查询后新建的作业不在旧事务的版本检查集合内。

在原移除事件事务中新增引用校验触发器，同时在作业插入/更新事务中拒绝新增已移除资料引用。范围沿用cargo_groups及links中documents/public_documents的字符串ID，包含历史成果及冻结分配。已有历史引用不重写、不扫描修复；资料仍软移除/恢复，R2不删除。旧v1库使用独立增量初始化键添加触发器，原表和事件数据不重放。移除及分组保存仍先沿用原权限、版本和幂等规则，仅将提交时冲突转换为原有语义的刷新/保留历史提示。

首阶段相关Node **29/0/0**，两项原生D1竞态 **2/0/0**；整批快照断言及R2对象数保持原值。尚待公共/归档引用、旧库双冷启动、回滚/幂等/权限、完整回归及实际页面验证。此阶段不申请发布，最终固定SHA交独立审核。
