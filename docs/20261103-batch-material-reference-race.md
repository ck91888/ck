## 双向竞争与第一阶段修复

1. 移除请求已读完同批作业列表，在提交事务前挂起；随后创建新作业并成功选择该资料，再放行旧移除。旧版仍返回removed=true。
2. 移除请求读完旧列表后创建新作业，新作业读到可用资料并在分组保存事务前挂起；旧移除先提交，再放行旧保存。旧版仍成功写入已移除资料的冻结引用。

两引擎均使用真实登录Worker API、本地合成SQLite或workerd D1：修复前 **0通过/2失败/0跳过**，失败即两项非法成功，日志保留在本地。并非只对原有作业做版本CAS就足够：初次列表查询后新建的作业不在旧事务的版本检查集合内。

最终实现是在任何资料/事件写入前，于同一DB.batch中核验初读的整批作业ID集合没有新增、删除或替换；结合原有每单事件/版本CAS，保证引用检查与所有子单变更通知覆盖同一集合。核验插入CHECK约束空表后在同事务立即删除，事务写锁持续至整批完成，失败回滚且不保留声明记录。即便新单没有冻结引用，也会要求旧移除/恢复刷新重试，避免漏发新单资料变更通知。引用仍沿用原cargoReferencesFile规则，包括公共文件、归档成果和冻结分配；没有新增每次作业更新时扫描JSON的触发器。

资料仍软移除/恢复，R2不删除，历史引用不重写。旧v1库使用独立增量初始化键添加空声明表，原表和事件数据不重放。权限、原有逐单版本与幂等规则不变，仅将提交时整批作业集合变化转换为原有“资料或关联作业已更新，请刷新后重试”提示。第二种竞争中旧移除先因新单出现回滚；重试移除覆盖新单、提高其版本，使原在途分组保存按原版本规则回滚。
