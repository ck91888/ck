# 部分到仓先理货

基线：测试分支 `42d76a669c4b3f5166251af5a931aa1163415897`。
分支：`feature/partial-arrival-putaway-20261103`。

## 阶段一：数量基础（尚未接入业务入口）

- 新增独立、不可修改的批次快照存储，不回填旧记录。
- 快递可理货量取服务端实际收货凭据，不取计划数量或客户端实收值。
- 车辆部分在原卸货完成前不计入可理货量；先到快递不伪造车辆卸货。
- 每批保存派工时的数量上限，后续到货不自动扩大旧任务范围。
- 同单位多行分配只记一次，拒绝超量、负数、重复单位、未知单位。

开发验证：`node --test tests/inbound-arrival-batches.test.mjs tests/inbound-stages.test.mjs tests/courier-arrival.test.mjs`，20 通过、0 失败、0 跳过。

此阶段未接入扫码、候选、派工或完成接口，不能作为功能完成或发布依据。
后续接入分批理货、数据库事务校验与旧触发器升级，再验证手机/PC、混合车辆到货、再次收货、最终完结和回归。
上架与整单完结继续保留齐货条件；直进直出、退件、换单沿原业务分流。

截图两份均能由 Library 查到，但官方材料化助手下载失败，目前未查看像素。
所有用例为本地合成数据，不操作线上业务记录。本分支不包含已暂停的 P1 修复分支。

## 阶段二：后端业务接入（待界面与完整回归）

- 部分已收快递允许扫码识别、候选选择与正常派工；零到货仍拒绝。
- 代发理货及大货理货上架可分批记录，完成事务重验原批上限与当前实收剩余量，重试不重复累计。
- 完成首批不完成整计划、业务子任务或外部单号；上架和整单完成仍等待齐货及各批理货。
- 首批快递理货不伪造车辆卸货里程碑；混合计划保留原车辆后到卸货入口。
- 迁移替换旧阶段/外部单号唯一索引及阶段触发器，保留旧版合并任务、历史产出和工时。非分批的完成单仍不能重复开工。
- 详情返回当前任务不可变的分批数量快照，供界面使用。

开发验证：

- Node SQLite 四组相关测试：28 通过、0 失败、0 跳过。
- 同一份新增 API 用例运行在真实本地 workerd D1：8 通过、0 失败、0 跳过。
- 覆盖两票两批、在途新增收货、超量/重复完成、首次扫码早于建计划、混合车辆后到、多单竞争同一实收量、大货分批、暂停恢复、事务故障回滚、旧索引与触发器升级保留历史劳动。
- 阶段二曾测得大货第二批被旧唯一索引拒绝，已修复；旧库模拟夹具漏删新触发器的测试错误已修正。原失败日志保留，最终上述重跑通过。

PC/手机真实表单、严格登录权限、全部测试与草稿/照片/返岗派审回归尚未完成。此阶段不发布。

## 阶段三：现场界面

- 详情显示快递到仓进度与部分理货状态；没有新的可理货数量时提示等待后续到货。
- 表单按当前任务批次显示可理货上限；刷新、重新打开仍读取同一服务端快照，不把第二批默认带成整计划数量。
- 分批作业只显示已到仓可操作的类型，不因车辆仍在卸货而阻止已到快递的本批理货；旧版任务保留原卸货完成校验。
- 真实 Chromium、严格工牌登录、返岗/自动派审开关开启：1440/390/320 三组全部通过。每组覆盖候选、识别、派工、刷新、超量失败不产生成果、首批结束、待到货、第二批数量上限、最终上架与无横向溢出。
