# 理货任务在系统截止后接续

行为基线是 `e23cda4f9bbb7e8e5e48453f417b064327cd18bb`。在远端性能提交之后保留普通向前回退提交，再提交本修复；不改写 Git 历史，不包含共享初始化/收尾 Promise、出库读取期限或其他未发布候选。

## 可复现的问题

使用合成数据创建并开始理货，执行已有 04:00 KST 收尾后，原作业变为 `system_closed`。单号进度只识别部分在途状态，把它显示为待理货且不返回任务 ID；开始入口也遗漏这个状态。再次开始尝试插入同一计划、外部单号、作业类型，碰到仍正确保留原任务的 `ck_inbound_stage_unique` 唯一约束。

这复现了相同的三个字段唯一键错误，但没有读取现场记录，不能据此断言现场旧任务一定是此状态。

## 处理

- 进度查询保留系统截止任务及其类型，标记待恢复，不把它算作已完成。
- 扫码识别到截止任务时，展示中韩说明和“打开原任务”，禁用新建开始。打开仅查看；恢复仍走已有人员确认、权限、在岗校验及审计流程。
- 原理货页面允许查看截止任务；恢复前禁止提交完成，确认恢复后恢复可操作状态。
- 后端对既有阶段任务给出业务提示；即使另一次开始在预检后赢得唯一键，也重新读取既有阶段状态，避免向用户暴露数据库错误。唯一索引和事务仍保留。

没有新增表、索引、触发器、迁移、记录状态或历史快照格式。没有改变截止计算、初始化、工时修正、人员占用、成果写入、库存或出库处理；没有自动恢复人员，也没有删除原任务。

## 验证范围

- 合成 API 回归覆盖：实际截止后识别、禁止重复开始、原请求重放不恢复、明确恢复及并发重试、旧工时和截止审计不变、完成一次；暂停、取消、已完成状态；新建竞争；失败事务重试；截止上架的原任务接续。
- 真实本地 workerd 中运行 staging API，通过独立 HTTP 请求和真实本地 D1 验证并发开始、截止、识别、恢复事务失败/重试、审计保护及单任务单成果。
- 实际浏览器在手机和电脑宽度执行识别、打开原任务、取消恢复、确认恢复、提交已落库但响应丢失后的重试，以及完成。检查中韩提示和无横向溢出；截图只保存在私有证据目录。
- 最终全量 1329/1329 通过，失败、取消和跳过均为0；构建、语法、差异检查和 staging 配置 dry-run 通过。
- 实际以原始 e23 Worker 接手候选版恢复的合成任务，验证同一任务可正常完成一次，数量正确且截止审计保留。

仅使用隔离合成数据，没有访问或修改现场业务数据。

## 回退兼容

本批保存的数据仍由既有 `sop_native_resume` 和完成接口写入，格式与 e23 一致。切回原始 e23 会重新出现识别截止任务的旧缺陷，但不会产生新增历史主键冲突、重复收货进度或需要撤销的数据迁移。快递快照候选不属于本修复。
