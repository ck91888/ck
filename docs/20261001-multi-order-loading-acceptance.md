# 一车多出库单装货验收记录

日期：2026-10-01。测试版 release：`20261001-multi-order-truck-loading`。

## 业务规则与改动

- 入口仍为现场执行 → 出库作业 → 出库装货。连续扫码与待出库列表多选可混用；重复单去重，误选可单独移除。本车上限20单。
- 本车统一派工，只创建一个装货任务。每个操作员按实际参与的时间段计时，关联单数不增加工时。车牌和司机为选填。
- 用户确认没有部分装货。本车所有单据均须核对完成，才允许结束；任何单少装、未审核、未下发、未确认资料变更或提货变更时，整车结果不会提交。
- 每张单保存自己的实装箱数、托数、出库状态；单据历史展示自己的数量。计划大于0的箱/托维度必须与实装一致；计划为0的维度为未指定，允许录入实际数量。例如按2托预约的货物，可以保存实际28箱、2托。
- 活跃任务独占各张出库单。重复请求、丢响应后的重试、刷新继续不重复建任务或工时段；整车结果、逐单出库、关闭人员计时在同一数据库事务中提交。
- 已有单单任务和历史记录保留。取消、查询历史、修改出库基准等逻辑同步识别本车第二张及后续单据。无单临时装货沿用原入口及逻辑。
- 新表与保护触发器仅在测试版功能开关开启时初始化；没有清空、回写或转换现有测试业务数据，没有修改正式版配置或部署正式版。

## 实际操作验收

数据来自隔离的内存SQLite，使用真实Worker API与实际构建的现场页面；没有用现有测试客户单据做出库操作。

| 场景 | 操作和结果 |
| --- | --- |
| 同车三单 | 虚拟东亚10箱、虚拟BD2托、虚拟极罗8箱，统一两人派工。生成一个任务、三条单据关联。结束后各单独立保存数量并成为已出库。另以API验证托数预约保存实际28箱、2托。 |
| 连续扫码与多选混用 | 浏览器扫描第一单，再次扫描提示已在清单；列表勾选第二单，扫描第三单。清单为3单，没有覆盖或重复。 |
| 移除误选 | 列表加入第四张误选单，再单独移除，其他三单保留。误选单仍待出库。 |
| 不符合装货条件 | 未审核单扫码提示公开单号及原因，列表无法勾选。API另外验证未下发、变更待确认、提货待确认、任务占用。无法用多选或直接请求绕过。 |
| 不接受少装 | 浏览器把第一单10箱改为9箱，结束被拒绝，提示对应出库单号。所有单和人员仍在作业。API验证缺单、重复结果、少装和负数都不会提交部分结果。 |
| 调整人员 | 装货中从甲、乙改为甲、丙；甲原计时段不重建，乙结算原段，丙新建一个参与段。页面保留逐单数量草稿。 |
| 刷新和返回继续 | 浏览器刷新恢复同一任务、三张单、已填写数量和甲/丙人员。返回首页显示一张本车任务卡，列出三张公开出库号和客户；再次进入恢复原数量。 |
| 完成后返回 | 正确填齐后结束，自动回首页，本车任务从现场在途列表移除；没有停在已完成详情。 |
| 数量与历史 | 真实API检查三张单的实装数、托数、状态，以及每张单历史的本单结果；第三单、第二单均能找到本车任务。 |
| 工时看板 | 控制时间案例：甲30分钟、乙30分钟、丙10分钟，总70人分钟，看板显示1.2人小时；不是按三张单累计为210分钟。 |
| 丢响应、并发、重复点击 | DOM测试在服务器成功后模拟派工响应丢失，刷新后重试仍为原任务，无需重新派工；模拟完成响应丢失后重试只有一份结果。API并发开始/结束、相同请求重放均没有重复数量或工时。 |
| 事务失败、并发变更 | 在第二单关联写入失败、提交时单据或作业版本变化、人员被其他任务占用等故障下，整车事务回滚，不留半个任务或半车已出库；提示带相关单号。旧单单完成过程遇到变更也回滚结果和计时关闭。 |
| 手机/PDA布局 | 在浏览器390×844及360×720视口操作和检查。无横向溢出，公开单号换行；实装箱数/托数每单并排，数字输入16px、输入/按钮至少44px高。 |

## 回归验证

`node worker-v2/build-sop-staging.mjs` 成功。全部224项测试通过，0失败、0跳过，包含新装货场景、页面DOM以及既有派工、卸货、作业计划、签到、资料和出库联动。

## 尚未验证

- 真实手机/PDA上的相机权限、摄像头扫码与硬件扫码枪输入。
- 现场真实弱网、Wi-Fi切换、锁屏或浏览器进程被系统回收；当前验证的是可控丢响应、重试和刷新。
- 真实Cloudflare D1的生产规模数据并发和端到端现场网络时延；本轮交易故障和并发验证使用隔离SQLite适配器，不等同于云端压力测试。
- 没有在现有测试业务单据上实际提交装货完成，以保留测试数据；上线后的版本及静态资源另做只读确认。
