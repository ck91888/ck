# FE-05 卸货照片刷新与实例缓存

基线为已发布测试`89709cb5634af5a2e683b17b54c2ef9642bc3b38`，独立分支`feature/fix-unload-photo-lifecycle-20261104`。本批只改卸货照片控件，不混入未放行的FE-03/04或重置补丁；不读写线上数据、不部署、不合测试/main。

## 原问题

原控件按作业/资料缓存实例，重进直接挂回旧DOM，不重新查询，因此看不到另一设备新增或移除的照片。实例Map也不清理，访问不同作业后保留全部离屏DOM。另有选择文件等待首次列表的窗口：文件尚未进入pending，旧`hasPending/flush`不知道这批选中内容。

有效基线专项 **2通过/7失败/0跳过**。旧失败队列同文件/同请求号重试与不同资料隔离控制通过；新刷新、缓存上限、选中文件保护、迟到读取及身份隔离失败。首轮夹具误绑定Node Crypto方法的`this`，修正夹具后重新测基线；原日志保留，不把该初始化错误当业务缺陷。

## 修复设计

- 重进同一归属的控件时重新读取服务器照片；在途读取合并。上传中要求的刷新等待上传结束，再读列表，避免旧快照覆盖刚保存的照片。刷新失败保留当前控件和队列，继续提供重试。
- 缓存最多保留16个没有待处理内容的离屏实例。当前页面上的控件及选文件等待中、压缩中、上传中、失败待重试的实例不淘汰；多计划同时可见不受此上限影响。干净实例回收只清除本地DOM/引用，旧在途响应不会重新写回；不删除服务器照片。
- 文件在第一次异步等待前捕获。`hasPending/flush/beforeunload`包含选择等待，后续文件选择可加入当前上传队列，压缩失败、网络失败或不完整成功回执均不移除文件。已压缩File与client_req_id在重试、重进和缓存压力下保持不变；明确移除或成功保存后撤销预览URL。
- 作业、资料类型/ID与当前操作身份分别隔离。身份变化后旧实例隐藏照片、不显示或发送旧队列；文件仍保留并参与离开保护。同一现场人员的正常15秒身份探测会替换user对象，按服务端人员/工牌/出勤身份保持队列，避免将正常探测当换人。实际权限仍由原列表/上传API每次校验，不把休息或派工资格变化当作另一人员。
- 原图片压缩组件、API权限/幂等、R2、12张/10MB及原字段规则不改。无新增跨登录持久化或跨账号队列转移，整页关闭仍使用原待上传离开提示。
