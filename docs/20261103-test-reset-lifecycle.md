## 最小修复

业务源码仅 `worker-v2/test-data-reset.js`：

1. 将明确业务表清单70→109，增加39张表；实际每次仍只处理数据库中已存在的表，不创建未启用业务模块，不按通配符删除。业务子表及事件在人员/作业/计划之前处理。文档版本首先备份并删除，使之后原有 DELETE 触发器的计数 UPDATE 不修改其备份值。原始工时不补签退，不改写历史事件。
2. step 发现旧活动重置遗漏当前业务表时，以 `tables_json` 原值及“未完成”条件 CAS 扩充范围并重新读取；保留原 run ID、所有已完成标记和备份。两个请求同时恢复不会覆盖清单或重复清空已处理表。已经完成的旧 run 始终只返回原回执，不自动扩范围删除新数据；如要清理更早已完成重置留下的旧残留，须由负责人另行显式启动新一轮，本开发未执行。

每表仍是“记录行数、建立备份、删除”同一事务，单请求最多四张表。某表删除失败，该表备份和标记回滚，其它已完成表不重复处理；错误保留供同一 run 恢复。最终发现已处理表出现新记录时仍拒绝完成并保留记录，未改成再次删除。

权限、两个测试域名、staging/功能开关/指定数据库标识、同源POST、专用请求头与显式确认均沿用原限制。账号会话、登录限流、操作人确认上下文、返岗/派审配置、库位、schema元数据和重置审计/历史备份继续保留。日当授权表与共享关系随其人员业务记录备份清除，不把残留授权关联到新一轮身份；旧现场会话按原身份验证失效，办公室会话仍可继续操作。R2附件原对象保留。

新增声明表分类测试：当前模块声明的业务表必须明确进入清理范围或明确列为保留控制表，避免后续新表无声遗漏；不会据扫描结果自动扩大删除范围。
