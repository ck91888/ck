# 库内操作及退件入库填写规则

基线：测试分支 `upgrade/sop-safe-rollout-20260917` 的 `e3f754611f8348388106ce23625874db7bd49f5e`。发布标识 `20261020-internal-return-metrics`，仅目标 `ck-v2-api-sop-staging` / `sop-test.ck91888.cn`。保留独立单号理货上架及此前功能，不合入 main，不更新正式环境。仓库及父目录未发现 AGENTS.md；执行用户提供的分支、保留数据及发布授权。

## 使用

现场执行 `/001` → 库内操作：

| 作业 | 开始时 | 结束时 |
| --- | --- | --- |
| 盲盘 | 明确选择盲盘；无需数量 | 盘点数量、货位数量、是否使用叉车 |
| 精盘 | 明确选择精盘；盘点数量、货位数量、是否使用叉车 | 不重复填写 |
| 废弃处理 | 拣货数量、货位数量、是否使用叉车 | 不重复填写 |
| 质检 | 正常派工 | 质检数量 |
| 仓库整理 | 正常派工 | 整理内容 |
| 入库 → 退件入库 | 原客户和开始备注保留 | 该批次退件入库单数、入库产品数；原工作说明和其他备注保留 |

数量与现有上架货位数使用相同业务范围：0 至 100000000 的整数。允许明确填写 0；未填写、空字符串、负数、小数、非数字、布尔值及数组/对象拒绝。叉车必须明确选择是或否，不设默认值。整理内容去除首尾空白后非空，最多 2000 字。前后端共用纯校验模块。

派工人员、工牌准入、部门权限、调整人员、暂停恢复、工时和完成路径沿用现有机制。开始快照由服务器记录；精盘及废弃开始数据不能在结束或通用补录中改写。新任务最后人员离开保留待收尾，管理员清理不能绕过所需完成数据。新退件必须走原退件派工及完成入口，不能用通用工时入口创建或完成。

## 保存与历史兼容

在原 `v2_ops_jobs.shared_result_json.internal_operation` 中记录版本 1、任务类型、盘点类型以及 start/finish 快照；快照包含服务端记录时间和已验证操作人 ID。完成沿用原事务和稳定结果主键，在 `v2_ops_job_results` 中每任务仅保存一条结果；与参加人数无乘法关系。失败回滚人员计时、状态、结果和幂等凭据。相同开始请求恢复原任务，变更内容的同请求拒绝；完成并发/重试不增加结果。

无版本快照的旧进行中任务沿用原完成规则，界面明确显示旧版及专项数据未记录，不强迫追溯开始数量。历史盘点不自动认定盲盘或精盘，导出类型和专项数值留空；旧版兼容标志单独导出。没有迁移、回填、批量清理或实际业务记录更改。重复完成已完成的上述类型不再顺带改写其遗留工时。旧备注和历史原始结果保留。

现场当前任务可见盘点类型和开始快照。数据中心 `/shuju` → 单子数据 → 详情 / 导出明细 CSV，可见填写时点、各项数量、叉车明确是/否、整理内容、两项退件数量、记录时间、操作人及原始版本快照。0 保留为数值 0，缺失留空，叉车 false 导出“否”。旧通用箱数/板数字段不冒充专项数量。
