# 协同作业单统一由大货按单操作执行

独立起点：测试分支 `upgrade/sop-safe-rollout-20260917` 的远程提交 `2f1fc8636091565e1babab486a6d10863fa5b8ab`。该检出版本没有 AGENTS.md 或 `.agents/skills`；执行本次用户授权及仓库验收规范。本页取代 2026-10-16 文档中“非大货协同作业单应拒绝派工”的业务结论。

## 行为与边界

- 协同中心的作业计划，以及关联的作业任务，统一使用大货执行权限。`work-execution.js` 为对象权限、查询过滤和交接 SQL 提供同一规则；不根据客户端提交的执行部门决定历史记录权限。
- 新作业计划明确记录 `execution_department: bulk`，新关联任务使用大货部门。作业计划原 `department` 保留来源/业务意义；既有作业计划、任务、工时、审核、来源单据和历史事件不批量重写。可选出库的原业务归属和计算规则保持原样。
- 历史 `direct_ship/import` 作业计划可以从原大货入口扫描，查看、取资料、单单及多单派工、分组多工序执行、换人、暂停恢复、交接和审核。本人任务列表、分组列表、打印、统计及创建回执查询使用相同执行规则；日当派审员也支持使用公开 ZY 作业单号派工。
- 新建库存作业计划固定说明“大货执行”；入库附带作业计划的原业务选项明确为“出库业务”。打印及现场页显示执行部门，不再显示阻拦人员选择的部门不符提示。不新增入口。
- 仍要求大货派工资格、当天有效签到、人员可用、任务归属和实际扫码接收人。交接安装新的事务触发器并移除旧的部门判断触发器；接收人撤权或原负责人复岗竞态仍会回滚。已移交的原派审员不能继续操作。
- 独立代发拣货、打包和进口原生任务仍按原部门授权。协同单规则不改变 `dispatch` 原生记录的部门判定，也不开放管理、导入、记账等办公室权限。
- 沿用现有批次劳动模型：一人多单必须一名操作员；只保留批次根计时，等待审核计时，第一张完整作业计划全部工序审核后释放人员并停止计时。后续按单报产及补工耗不重开批次计时、不关闭人员的新任务。操作人员无需登录 PDA。
- 浏览器验收发现工牌登录初次响应缺少签到身份字段，后续轮询会误判为人员变更。页面接受工牌登录前读取完整服务器身份；真正换人、撤权、签退及旧响应隔离仍有效。
