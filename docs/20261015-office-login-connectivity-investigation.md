## Read-only backend audit

The backend is unchanged from deployed `6e19d833`. Non-OPTIONS API requests enter business schema initialization before `sessionAction` (`worker-v2/index.js:12887` and `:12943`). Most initializers cache success by DB binding; this is not a full migration on every request. Warm API requests still read maintenance/session/operator state. These are potential latency contributors, with no measured server timings to attribute the reported delay to them. In contrast, the two slow static JavaScript files shown in the screenshot go directly through `ASSETS.fetch` and bypass those API/session database steps (`worker-v2/staging-entry.js:12`). No application `Server-Timing` or trace-duration response headers were found. Even a long Waiting for server response phase in browser Timing would include network time and would not, by itself, prove slow database execution.

Regular business responses use `new Response(JSON.stringify(obj), ...)` (`worker-v2/index.js:58`) after awaiting handlers (`:13027`). Login commits its database batch before constructing the JSON Response (`worker-v2/access-control.js:114`); identity uses `Response.json`. No asynchronous streaming JSON implementation was found. For these paths, business computation and serialization occur before the response is returned and cannot directly explain the later 17.23-second body-reading phase. The `/api` attachment action can instead return an R2 body stream (`worker-v2/index.js:7248`), so the screenshot's unknown action must not be assumed to be ordinary JSON.

## Isolated mitigation

`shared/sop-session.js` gives authentication requests bounded waits covering both response headers and JSON body consumption. Login, identity lookup, operator confirmation and logout each allow up to 60 seconds. The login gate shows elapsed time and, after 8 seconds, a slow-connection message while continuing to wait. Business mutations have no added retry or timeout. A timeout explicitly leaves the server result unknown, re-enables controls and offers an office-only read of current login status. Password submission is never automatically repeated. Genuine server credential rejections retain their existing result. A late identity result from before a newer login cannot overwrite or lock that login.

Authentication policy, password verification, API routes, backend schema and production data are unchanged. Successful login still requires the original server session and operator confirmation. Password input is retained only in the existing input on an uncertain failure and is never written to storage or logs.

The initial local 8-second identity and 15-second login deadlines were removed after observing successful 16–22-second requests. The final 60-second deadlines have been checked with actual 22.5-second browser responses for login, identity and operator confirmation. The response-reading delay and underlying regional connectivity remain separate unresolved issues; do not describe this release as a regional connectivity fix.
