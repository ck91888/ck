# 并发初始化与列表读取等待修复

基线 `e23cda4f9bbb7e8e5e48453f417b064327cd18bb`。仅发布测试分支 `upgrade/sop-safe-rollout-20260917`、Worker `ck-v2-api-sop-staging`、测试站 `sop-test.ck91888.cn`。保留取消入库重传修复、人员占用一致性和韩国时间04:00收尾。资料分组候选未包含在本批。

## 已确认的问题与边界

原代码的通用schema初始化只缓存成功，没有合并同一DB、同一版本的首次并发执行。所有API在业务处理前等待系统收尾补处理；当日完成标记缺失时，并发请求也会各自准备和提交收尾事务。出库列表直接等待完整JSON，没有读取期限或取消旧请求，响应体挂起会一直显示加载中。

这些问题在原基线的本机合成夹具中已复现。尚未取得现场慢请求的阶段耗时或线上D1日志，也未复现国内55秒等待，不能将其认定为该次现场故障的完整原因。

## 实现

- `schema-ready.js` 按DB绑定和版本共享正在进行的初始化。成功才进入就绪缓存；失败向全部等待者返回并清除进行中状态，后续可重试。没有缓存身份、权限、会话或业务数据。
- `system-cutoff.js` 按DB绑定和当日KST边界合并正在执行的补处理。不同数据库或不同日期分别执行，已完成请求仍核对数据库标记。
- 收尾标记、原始快照、审计和执行状态更新仍在一个D1事务内。事务第一条语句取得该日处理权，每个扫描和更新都检查所属token；其他实例在预检后赢得处理权时，本实例跳过行扫描。任一步失败，标记和所有更新一起回滚，重试不会遗留“已完成但未处理”的标记。
- 没有修改04:00时刻、定时配置、最早跨越边界的计算、未核实工时口径、原任务续作、人员占用或成果/出库保护。
- 出库列表复用读取期限：8秒后提示等待，60秒后显示失败和手动重试。期限覆盖响应头与完整响应体；即使底层读取未响应取消，也能结束页面等待。新筛选、再次查询或离开tab会取消旧读取；旧请求不得改写新列表或提前解锁新查询按钮。筛选值保留，不自动重试写操作，不把超时显示为空列表。

没有修改DNS、域名、路由、CORS、认证、安全配置或线上业务数据。
